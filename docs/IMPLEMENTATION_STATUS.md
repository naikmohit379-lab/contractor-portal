## Existing PRD implementation gaps

These are requirements already present in project documents, not newly proposed features.

### Recently implemented from the existing PRD

**REQ-DOC-4: Attach the original RoofV report to its measurement record.** Automatic retrieval is implemented in source and pushed to the `staging` branch in commit `ac921ae`. After retrieving measurement JSON, the server requests RoofV's saved-job report PDF when the provider returns a RoofV job ID; it verifies PDF bytes/size and stores the file privately with SHA-256 and retrieval metadata on the exact tenant/job/report. Authorized job readers download it through an authenticated route. Manual PDF upload is intentionally excluded. If the PDF is not yet available or the job ID is missing, measurements remain usable without an attachment and a later free report refresh can retry retrieval. Retrieval is audited; measurement values are unchanged. On 2026-11-11, the focused RoofV provider suite passed 6 tests; the complete API suite passed 128 tests across 24 files; shared tests passed 39 across 9 files; estimate tests passed 5; API and web typechecks passed; and the API bundle built. The web production build compiled and generated static pages but failed copying standalone traced files because Windows denied symlink creation. `next lint` reached an interactive ESLint setup prompt because no lint configuration exists; it was canceled without creating a config. Manual staging browser inspection confirmed the automatic PDF section is present and manual PDF upload controls are absent. Refreshing the existing Koramangala RoofV record returned a provider failure; no PDF was attached and no second order was submitted. GitHub CI passed for feature run [#71](https://github.com/naikmohit379-lab/contractor-portal/actions/runs/43003306078) and documentation run [#72](https://github.com/naikmohit379-lab/contractor-portal/actions/runs/43004939510), including 34 browser tests passed and 4 skipped. The staging Vercel alias served the app; the Vercel dashboard session was logged out, so the exact deployment commit/Ready status was not independently confirmed. Provider-success validation remains pending.

### Other existing implementation gaps

- **Document workflow:** Per-job folders and a complete category/lifecycle model are incomplete. Offline notes and a cached offline app shell are not implemented.
- **Supplier invoices:** Current variance is a high-level invoice/order comparison. Invoice-line extraction is not implemented.
- **Reporting:** Large report exports as background jobs are not implemented; current reports are basic/partial.
- **Security/privacy:** The PRD lists MFA/SSO, sensitive-field encryption beyond currently protected provider credentials, malware scanning for uploads, and comprehensive privacy export/deletion controls as missing. Retention and deletion requirements need CA/counsel review before implementation. No specific MFA method has been selected.
- **Localization:** Hindi text exists with English fallback; fluent Hindi product review remains outstanding.
- **RoofV:** The adapter, quota check, ordering, report retrieval, automatic original PDF fetch, and authenticated PDF download exist in source. Manual PDF upload is excluded. Provider access/terms and account limits need confirmation; returned quantities need review/site verification. Ambiguous-building selection and unattended signed-webhook/scheduled report updates are not implemented. Clicking **Refresh existing RoofV report** returned the UI to the same failed state. Vercel runtime logs for the Ready staging deployment showed the refresh endpoint returning HTTP 202 and a subsequent measurements GET returning 304, but no RoofV provider error entry was present in the selected log window. Therefore the provider failure cause and successful PDF retrieval remain unverified; no new measurement order was requested.

**RoofV queue follow-up (2026-11-13):** Code inspection confirmed the refresh path still launched `processReport` with `setImmediate` in the Vercel API process; Vercel logs showed a 300-second runtime timeout. Source now dispatches RoofV reads and automatic PDF retrieval through the Upstash QStash `roofora-measurements` queue. The callback verifies the raw-body QStash signature, validates the message, restores tenant context from the saved report, atomically claims work, and acknowledges duplicate/stale deliveries safely. It only reads an existing `roof_id`; it does not order measurements. The QStash delivery forwards Vercel's server-injected Protection Bypass for Automation secret and marks it for redaction in QStash message logs. Local verification before deployment: API typecheck passed; API bundle built; API suite passed 136 tests across 26 files; `git diff --check` passed. GitHub Actions run #80 passed all three jobs. QStash credentials remain Preview-scoped and their values were not inspected. The queue enable flag and callback URL are Preview variables scoped to `staging`. Vercel Preview redeploy `AFqCUWnzxabAgA9ofeb2HjPFNAbR` for commit `59cf217` reached Ready, but `/api/v1/health` returned HTTP 500 and Vercel runtime logs showed the function could not resolve `@upstash/qstash`. The package was missing from the API bundler's `noExternal` list. A local fix now adds the dependency to the bundle list; API typecheck and bundle passed, and the full API suite passed 136 tests across 26 files (the suite required localhost access for its temporary MongoDB replica set). The fix and updated documentation still need to be committed, pushed, and deployed to staging. Queue delivery and existing-report refresh are not yet verified. Do not create another measurement order. Production remains unchanged.

## Open product decisions and intentionally later scope

- Confirm one accountable Company Owner and the Project Manager/Operations Intern permissions. The current system permits an Owner to invite another Owner; the exact single-owner/delegation rule is undecided. The long-term Operations Intern role is also undecided.
- The company Admin Panel is currently a read-only, company-scoped triage overview. Direct editing from that panel is not implemented. A cross-company Roofora Platform Admin is not approved in the current PRD.
- Razorpay API refunds, link cancellation, and full provider reconciliation are not implemented. They are later scope; the current test flow does not initiate refunds.
- Supplier API/EDI, delivery verification, returns/reordering, SMS, and large background exports are later scope, not prerequisites for the first MVP unless reprioritized.
- The backup restore drill remains deferred, as previously requested. No database reset or destructive migration is planned.
